# 分析：DeepSeekHarness 适配的三级管道与门控

**目的**：回答"什么可以实现、什么没必要引入"。
**结论先行**：**工具层能硬强制，流程层不能**。包想要的大部分是流程层，硬做成钩子只会产生包自己明令禁止的东西——「以提示词冒充强制机制」。

| | 判定 |
|---|---|
| ✅ **可以实现，且值得做** | 敏感动作的**人工审批门**（`deny`/`ask`）、**资源枚举类**破坏性操作拦截、派发**记账** |
| 🔁 **没必要自建**（平台已有，且更好） | 工作区路径沙箱、钩子调用审计轨迹 |
| 🚫 **不该硬做**（只能软约束） | 三级分诊、独立 QA、工件顺序、任务合同完整性、"变更后门失效" |
| ⛔ **平台做不到**（必须诚实标注未复刻） | 从工具层识别子 Agent 的角色、改写工具输入、读取对话内容 |
| ✂️ **该砍掉**（做了反而有害） | **按文件名/目录名判定权限**——`Dockerfile`、`docker-compose.yml`、任何 `deploy/`、`k8s/` 路径段。它会把正常工作锁死，然后整套门控被一起关掉 |

> **最重要的一条发现**（第五节）：这套门控**已经建好了**，2026-10-14 被整体关闭。
> 关掉的原因**不是"不该有门控"，而是规则面铺得太宽，把日常开发动作也锁了**——
> 一条永远正确但让正常工作无法进行的规则，会连带把真正有用的规则一起拖死。

## 一、前提：DSH 的强制点在工具层，不在流程层

这是整份分析的支点。DSH 能**强制**的只有**工具调用**：

```
模型想调工具
   ↓
PreToolUse 钩子         → allow / deny / ask
   ↓
dsh-user-approval       → ask 时转人工，缺省 fail-closed
   ↓
dsh-sandbox-policy      → read-only / workspace-write / danger-full-access
   ↓
工具真的执行
```

它**没有**、也不可能有"这个回答必须先有过 Test Spec"这种检查点——因为那不是工具调用，是推理过程。

包里的门分两类，混在一起谈就会得出错误的设计：

| 门的类型 | 例子 | 能否硬强制 |
|---|---|---|
| **工具层** | 不写 `.env`、不跑 `kubectl apply`、不删数据库 | ✅ 能 |
| **流程层** | 独立 QA、先设计后实现、工件顺序、revision 失效重验 | ❌ 不能 |

包自己也承认了这一点，`02-复刻方案.md` §5：

> 原 OMP 正则只覆盖列举的命令和工具入口，**不能等同全面安全隔离**。……并在 **OS/容器层做真正隔离**。

以及 `04-验收清单.md` 的通过口径：

> 平台欠缺 hook、文件权限或独立成员能力记**未复刻**。
> **禁止以提示词输出"我会遵守"替代工具层或 OS 层证据。**

所以这份分析里，凡是流程层的门，我一律标"软约束"，不会包装成"已门控"。

## 二、DSH 原生能力盘点（全部有据可查）

### 2.1 已有的基础设施包

|---|---|

| `dsh-fs-sandbox` `dsh-bash-sandbox` `dsh-pwsh-sandbox` `dsh-sandbox-local` | 各能力的沙箱执行体 |
| `dsh-user-approval` | `ask` 策略 → 转人工审批；`never` → 直接拒绝；缺省 **fail-closed** |
| `dsh-client-ui-approval` | 审批 UI |
| `dsh-fs-observation-policy` / `dsh-session-checkpoint-policy` / `dsh-tool-call-timeout-policy` | 其它策略 |

`~/.dsh/profiles/desktop/cordis.patch.yml` 里 **`dsh-hooks-claude-code` 目前被注释掉**（第 58-67 行），注释写明是 2026-10-14 按"去门控"决定关闭的，材料仍在 `~/.dsh/team/`。

### 2.2 钩子协议的能力边界（关键证据）

`@deepseek-ai/dsh-hooks-claude-code/lib/index.js` 支持的 7 个事件：

```
SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, Stop, SubagentStart, SubagentStop
```

| 事件 | 能做什么 |
|---|---|
| `PreToolUse` | **阻断**工具，或**要求审批**（`ask`） |
| `PostToolUse` | 用反馈阻断结果，或附加上下文 |
| `UserPromptSubmit` | 阻断提示词，或附加上下文 |
| `SubagentStart` / `SubagentStop` | 给运行中的子 Agent 附加上下文 / 仅观察 |
| `Stop` | 强制再走一步 |
| `SessionStart` | 注入模型可见的上下文 |

**钩子的输出契约**（`dsh-hook-protocol/lib/index.js` 的 codec）：

```json
{ "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "allow" | "deny" | "ask",
    "permissionDecisionReason": "…",
    "additionalContext": "…"
} }
```

- `exit 2` → 阻断，**stderr 作为模型可见的理由**
- 顶层 `decision` 只认 `approve`/`block`；`allow`/`deny`/`ask` 必须放在 `hookSpecificOutput.permissionDecision`
- 合并优先级 **`deny > ask > allow`**
- 其它任何非零退出 / 崩溃 = **非阻断**（工具照常执行）→ **所以策略程序必须自己 fail-closed**

### 2.3 三个必须知道的硬限制

从 `dsh-hooks-claude-code/lib/index.js` 的载荷构造函数直接读出：

```js
function base(agent, event) {
  return { session_id: agent?.session.header.id ?? "",
           transcript_path: "",                       // ← 恒为空字符串
           cwd: agent?.session.header.cwd ?? process.cwd(),
           hook_event_name: event };
}
function preToolPayload(exec) {
  return { ...base(exec.agent, "PreToolUse"),
           tool_name: exec.name, tool_input: exec.arguments, tool_use_id: exec.callId };
}
function subagentPayload(event, info, child) {
  return { ...base(child, event), agent_id: info.id, agent_type: SUBAGENT_TYPE };
}
```

| 限制 | 后果 |
|---|---|
| **载荷里没有"角色"字段** | `SubagentStart` 只有 `agent_id` + 常量 `agent_type`。**钩子无法知道这个子 Agent 是 `qa` 还是 `backend`。** |
| **`transcript_path` 恒为 `""`** | 钩子读不到对话内容，无法做任何语义判断 |
| **`updatedInput` 被记录但不生效** | 钩子**不能改写**工具输入。路径归一化只能用于自己的判定，不能"修正后放行" |
| 载荷无 `permission_mode`（本方言） | 钩子不知道当前沙箱档位 |

**但有一个好消息**：`preToolPayload` 用的是 `base(exec.agent, …)`，即 `session_id` 是**发起该调用的 agent 自己的会话 id**。子 Agent 的工具调用带的是子 Agent 的 session_id。配合 `SubagentStart` 给出的子会话 id，**"这个调用是不是来自子 Agent"是可以判定的**（需要钩子维护状态）。

> 注意：`SubagentStart` 里 `base(child, …)` → `session_id` 是子会话 id，`agent_id: info.id`。所以判"是不是子 Agent"可行，判"是哪个角色"不可行。

## 三、包的五项最小接口 → DSH 逐条判定

包在 `02-复刻方案.md` 定义了它认为目标平台必须建立的 5 个接口。

### ① intake（三级分诊）

| | |
|---|---|
| 包要求 | 输入用户任务与项目规则 → 输出**路线、触发原因、需要的决策/授权** |
| DSH 机制 | 无原生"路线"概念。`AGENTS.md` 每轮注入；`UserPromptSubmit` 钩子理论上可拦 |
| **判定** | **🚫 不该硬做，软约束正确** |

硬做的样子：`UserPromptSubmit` 钩子正则检查模型回答里有没有"Fast/Standard/Deep"。
为什么不该做：**必然误判**。模型说"这是个小改动"和说"走 Fast"语义相同；反过来，模型可以为了过钩子而写关键词（这恰恰就是包禁止的"以提示词冒充强制"）。

正确做法（**已实现**）：写进 `~/.dsh/AGENTS.md`，路线是**声明**，用来决定"启用哪些门"，不是开关。

真正值得做的补充：让**路线**与**审批门槛**挂钩——见第六节。

### ② task dispatch（任务合同）

| | |
|---|---|
| 包要求 | 完整合同 + 角色 ID + 允许路径 → **批次标识、不可越权范围、派发前账本记录** |
| DSH 机制 | `subagent` 的 `tool_input.prompt` 在 `PreToolUse` 里**可见** |
| **判定** | **部分可实现**：记账 ✅ 硬做；合同完整性 ⚠️ 只能软提醒 |

- **记账**：`PreToolUse` matcher `subagent|subagent_fork|workflow` → 解析 prompt 里的角色 id → 追加 JSONL。**可以实现**（已有实现）。
- **合同完整性**（"允许路径"等 9 个字段是否写全）：技术上能正则拦，但**不建议阻断**：
  - 派发会被同义词、表格、自然语言表述绕过（不是恶意，是正常表达）
  - **每次派发弹一次审批，会让人直接放弃使用这套工作流**
  - 务实做法：缺失时返回 `additionalContext` 提醒，**不阻断**
- **"不可越权范围"**：钩子只能看到 prompt 文本，无法把它变成真正的路径约束。真正的范围约束来自：`sandbox-policy` 的工作区边界 + 派发时给子 Agent 写明的允许路径（**软**）。**不要假装它被强制了。**

### ③ artifact registry（工件登记与 revision 绑定）

| | |
|---|---|
| 包要求 | 类型/owner/源工件/revision/status → 依赖顺序、草案/批准区分、**旧 revision 门失效** |
| DSH 机制 | 无原生工件登记。但有 git，且包自己说"与代码版本相关的工件留在目标仓库" |
| **判定** | **🚫 不该自建注册表；✅ 该做的是"文件 + revision 字段 + 可核查"** |

为什么不自建 JSON 注册表（`~/.dsh/team/manifest/` 这类）：
1. **git 已经是 revision 的事实来源**（commit SHA / 工作树快照），自建一份必然与之漂移
2. 工件本身就该在仓库里、跟代码一起 review
3. 又一个需要同步的状态

该做的：工件就是**普通文件**，头部带 YAML front-matter：

```yaml
---
type: Tech Spec
owner: architect
source: PRD#v2
revision: 8f3c1a9        # 或 worktree-snapshot:<hash>
status: draft            # draft | approved
---
```

"变更后旧门失效" = 报告里记录被审 SHA，比对当前 SHA 是否一致。
**这是检查（check），不是拦截（enforce）**——钩子无法阻止有人引用旧报告。别把它说成门控。

### ④ policy hook（策略钩子）—— 唯一真正能硬强制的

| | |
|---|---|
| 包要求 | 工具调用、归一化路径、actor、任务授权记录 → **allow/block + 原因**；与文件系统权限**双层防护** |
| DSH 机制 | **完全具备**：`hook-protocol` + `hooks-claude-code` + `sandbox-policy` + `user-approval` |
| **判定** | **✅ 可以实现，且 DSH 上比包原文更强** |

比包强在哪：包的 `extension/index.ts` 只能 `{block: true, reason}`，**只有硬阻断**。
DSH 多一档 `permissionDecision: "ask"` → 转 `dsh-user-approval` → **弹人工审批**，缺省 fail-closed。

这正是包想要但做不到的：`RULES.md` 反复说"需**明确用户授权**"，而硬阻断只能拒绝、不能授权。**`ask` 让"请求授权"成为一个真实动作**，而不是提示词里的请求。

"双层防护"也满足：钩子（策略层）+ `sandbox-policy`（文件系统层）。

### ⑤ gate report（门控报告）

| | |
|---|---|
| 包要求 | revision/工作树身份 + 验收标准 + 实际执行证据 → pass/risk/block/needs-decision；变更后重验 |
| DSH 机制 | 无原生。报告就是文件 |
| **判定** | **🚫 无法强制内容真实性；✅ 可以做格式约定 + 可核查** |

钩子**无法判断**"这份 QA 报告是不是真的独立验证过"、"这个测试是不是假测试"。
能做的是：
- 规定报告格式（一个 skill）
- 报告必须带 `revision` 字段
- 已有技能 `verification-before-completion`、`anti-fake-testing`、`qa-delivery` 提供方法

**必须诚实标注**：这三道独立门在 DSH 上是**声明式**的，不是强制的。

## 四、包的工具层规则：逐条实测判定

包 `sources/omp/extension/index.ts` 的全部拦截规则，以及它们**在当前部署的适用性实测**：

### 4.1 命令规则（`BLOCKED_BASH`，第 7-12 行）

```
/\b(?:kubectl\s+(?:apply|delete)|terraform\s+(?:apply|destroy)|helm\s+upgrade|docker\s+push)\b/i
/\brm\s+-[A-Za-z]*r[A-Za-z]*f[A-Za-z]*\b/i
```

| 规则 | 实测 | 判定 |
|---|---|---|
| `kubectl apply/delete` | **kubectl 已安装** | ✅ **值得做** —— 明确的生产副作用，命令形态稳定，误判率低 |
| `docker push` | **docker 已安装** | ✅ 值得做，同上 |
| `terraform apply/destroy` | **terraform 未安装** | ⚠️ 当前永不触发；保留成本低，可留 |
| `helm upgrade` | **helm 未安装** | ⚠️ 同上 |
| `rm -rf` | — | 🔁 **不该用正则做** |

关于 `rm -rf`：正则**永远不全**。`find . -delete`、`rsync --delete`、`git clean -fdx`、脚本内部的 `rm`、`python -c "shutil.rmtree(...)"` 全部绕过。
包自己说"不能等同全面安全隔离"。
**真正的破坏性操作门应该是"授权 + 回滚工件"**（包 `RULES.md` 也是这么写的：逐项清单 + 单独确认 + 删除前后核对），而不是模式匹配。
正则可以做**兜底提示**，但不能作为"已防护"的证据。

### 4.2 受保护路径（`protectedPath`，第 24-41 行）

| 路径 | 当前部署实测 | 判定 |
|---|---|---|
| `.env` / `.env.*`（除 `.env.example`） | ✗ 不存在 | ✅ **值得做** —— 形态稳定、项目无关、误判率低 |
| `.gitlab-ci.yml` | ✗ 不存在；全盘也无 GitLab CI | ⚠️ **项目相关**，不该写进全局钩子 |
| `deploy/k8s/{test,prod}`、`deploy/monitoring` | ✗ 不存在 | ⚠️ 同上 |
| `/Users/lmqhx/wiki/raw` | ✗ 不存在（vault 未配置） | ❌ **本部署无意义** |

**结论**：包的路径规则里**超过一半在当前部署一次都不会触发**。这比"没有防护"更糟——它会制造**虚假安全感**（"我有策略层"），而实际防护为零。

正确做法：**按项目配置**，而不是写死一个全局列表。全局只保留真正项目无关的（`.env`）。

### 4.3 子 Agent vault 只读（`evaluateSubagentVaultWrite`，第 43-53 行）

| | |
|---|---|
| 包要求 | 专业子 Agent（无 UI 者）不能写 vault |
| DSH 可行性 | "是不是子 Agent"**可判**（靠 session_id 与 `SubagentStart` 关联）；"是哪个角色"**不可判** |
| **判定** | ❌ **本部署无 vault，无意义**；若将来接入，需按会话关联实现，且无法按角色细分 |

### 4.4 包自己已经移除的规则（重要先例）

`index.ts` 第 8-9 行的注释：

> 2026-09-16 依仓库所有者授权**移除 git commit/push 拦截**：提交与推送改为宪法 §四的**流程门控**（用户确认 + handoff 强制门控），**不再在工具层硬拦**。

**包自己已经承认**：有些门不该在工具层做，而该交给流程。
这是支持本分析核心结论的、来自包自身的最好证据。
所以"拦 `git commit/push`"属于**没必要引入**——而且包比我们更早得出了这个结论。

规则代码也从包的 2 条扩到 20+ 条：`SECRET_ENV`、`SECRET_KEY_FILE`、`SECRET_SSH_KEY`、`SECRET_DSH_CREDENTIALS`、`SECRET_DIRECTORY`、`CI_CD_CONFIG`、`PROTECTED_DEPLOY_PATH`、`DEPLOY_NO_AUTH`、`DOCKER_PRUNE`、`DOCKER_REMOVE_UNSCOPED`、`DOCKER_COMPOSE_BLANKET_DOWN`、`DB_DESTRUCTIVE_NO_AUTH`、`DB_DESTRUCTIVE_UNSCOPED`、`RESOURCE_DELETE_NO_AUTH`、`RM_RECURSIVE_FORCE`、`PACKAGE_PUBLISH_NO_AUTH`、`RELEASE_PUBLISH_NO_AUTH`、`VCS_PUBLISH_NO_AUTH`、`VAULT_RAW_IMMUTABLE`、`OUTSIDE_WORKSPACE`、`TASK_CONTRACT_DENIED_PATH`、`DISPATCH_UNAUTHORIZED`、`LEDGER_RECORD_MISSING`、`MALFORMED_INPUT`、`POLICY_INTERNAL_ERROR`。

**fail-closed 的实现尤其值得引用**（`policy_check.js:1378-1385`）：

```js
} catch (error) {
  // Last-resort fail-closed guard: an uncaught throw would exit non-2 and the
  // bridge would treat it as a non-blocking failure, letting the tool proceed.
  deny('POLICY_INTERNAL_ERROR', { … reason: `Refusing to run: the policy program threw …` });
}
```

它准确抓住了 **"崩溃 = 非阻断 = 工具照常执行"** 这个陷阱——这正是 2.2 节说的、必须自己兜底的地方。

### 5.2 但有一个**实质性缺口**：`needs_auth` 被硬拒绝，没有用原生审批

`policy_check.js:1157-1170` 的分发逻辑：

```js
const blocking = findings.find((f) => f.kind === 'outright');
if (blocking) deny(blocking.code, { … });          // exit 2

const gated = findings.filter((f) => f.kind === 'needs_auth');
if (gated.length > 0) {
  const candidates = ctx.authorizations;
  for (const finding of gated) {
    if (!匹配到记录) {
      deny(finding.code, { …,
        reason: `${finding.reason} No matching record was found in the payload or in ${authorizationsPath()}.` });
    }                                                 // exit 2  ← 缺口在这里
  }
}
allow(ctx);                                           // exit 0
```

**语义已经分好了，但输出通道只用了 `deny`。**

问题：
- 包 `RULES.md` 要的是"需**明确用户授权**"，而 `exit 2` 只能**拒绝**，不能**请求授权**
- 硬拒绝会逼模型换个写法绕过，而不是来问用户——这恰恰降低了安全性
- 现有实现全篇**没有 `permissionDecision`**，即没有用到 DSH 的 `ask` 通道

**建议的改法（很小，一处）**：

| 判定 | 现在 | 应该 |
|---|---|---|
| `outright`（wildcard 清理、未命名删库、`rm -rf` 越界） | `exit 2` | **保持 `exit 2`** —— 这些不接受任何授权，就该硬拒 |
| `needs_auth` **且**有匹配授权记录 | `exit 0` | 保持 |
| `needs_auth` 且**无**匹配记录 | `exit 2` ← | **改为 `permissionDecision: "ask"`** |

改完之后带来的好处（有据可查）：

1. **"请求授权"成为一个真实动作**，而不是提示词里的请求
2. 用户的批准**就是**授权记录；`dsh-user-approval` README 明确写：
   > *Every request and outcome is recorded in the requesting session's **audit log**.*
   —— 审计轨迹由平台产生，不用自己造
3. 缺省 **fail-closed**（`unavailable` 即失败），符合包的安全要求
4. 保留了 `authorizations.json` 这条"预授权"快路径：已授权的照旧直接放行，不打扰用户

### 5.3 过度阻断清单：**这才是它被关掉的真正原因**

对 54K 程序做完整精读后（含实跑验证），发现的不是"防护不足"，而是**规则面铺得太宽，把正常开发动作一起锁了**。而且 `protectedPath` 的检查**优先于**契约白名单（`policy_check.js:1195-1200` 在 `:1213` 之前），所以下面这些是**授权记录也解不开的硬墙**：

| 规则 | 触发条件 | 为什么是问题 |
|---|---|---|
| `CI_CD_CONFIG` / `cicd.protected-config` | basename 命中 **`Dockerfile`、`Dockerfile.*`、`docker-compose*.y(a)ml`、`compose.y(a)ml`**、`Jenkinsfile`、`.travis.y(a)ml`、`azure-pipelines.y(a)ml`、`bitbucket-pipelines.y(a)ml`、`.gitlab-ci.y(a)ml` | **`Dockerfile` 和 `docker-compose.yml` 是日常开发文件，不是"CI 配置"**。任何容器化项目一改就被硬阻断 |
| `CI_CD_CONFIG` / `cicd.github-workflows` | 路径含 `.github` 且其后出现 `workflows` | 改个 GitHub Actions 就被锁 |
| `PROTECTED_DEPLOY_PATH` / `deploy.protected-directory` | **任何**路径段等于 `deploy` | 一个叫 `deploy/` 的**普通目录**就全盘锁死，包括放文档、放脚本 |
| `PROTECTED_DEPLOY_PATH` / `deploy.k8s-directory` | 任何路径段等于 `k8s` / `kubernetes` | 同上 |
| `SECRET_ENV` / `secret.env-file` | `.env` 与 `.env.*`；**`.env.example` 默认也被拦**，要 `DSH_TEAM_ALLOW_ENV_TEMPLATES=1` 才放 | 模板文件被当成机密 |
| `VAULT_RAW_IMMUTABLE` / `vault.raw-tree` | 路径含 `raw` 段，**且**父段名匹配 `wiki\|vault\|obsidian\|knowledge[-_]base\|notes` | **启发式**：一个 `notes/raw/` 目录就被锁 |
| `PATH_ARGUMENT_MISSING` / `path.missing` | 工具输入里读不到已知路径键（只认 `file_path`、`path`、`file`、`filePath`、`patch`） | 任何用别的键名传路径的写入工具**直接判死** |

**结论**：问题不是"该不该门控"，而是"门控的**粒度**错了"——把**文件名**和**目录名**当成了权限信号。

**这正是"没必要引入"的最有力论据**：一条永远正确、但会让正常工作无法进行的规则，等于没有规则——因为它会被整体关掉，连带把真正有用的那几条一起关掉（本部署的真实历史就是如此）。

### 5.4 与包的背离：git 被重新门控了

包的 `extension/index.ts:8-9` 记录了 2026-09-16 的决定：

> 2026-09-16 依仓库所有者授权**移除 git commit/push 拦截**：提交与推送改为宪法 §四的流程门控，**不再在工具层硬拦**。

但现有实现有规则 `VCS_PUBLISH_NO_AUTH`（`git.commit` / `git.push`，需 `vcs_publish` 授权，实测 `git commit` / `git push` / `git -C /tmp push` 均 exit 2）。

**这是背离包自身决定的**。两条路，二选一，但必须明确选：
- **改回包的决定**：去掉 git 规则，交给流程（`AGENTS.md` 已声明"提交、推送需明确授权"）
- **保留并记录理由**：明确写成"本部署有意强化"，而不是悄悄与来源不一致

我倾向前者 —— 因为包移除它的理由（"硬拦会逼绕过，不如流程门控"）在这里同样成立，而且 git 是**可恢复**操作（reflog / 远端），风险等级远低于删库。

### 5.5 结论：不是"要不要建"，而是"开哪几档"

| 资产 | 建议 |
|---|---|
| `policy_check.js` + `hooks.json` | ⚠️ **不能原样重开**。必须先削掉 5.3 那张表里的过度阻断，再启用 |
| ↳ 削完之后 | 🔁 重新启用，并改一处：`needs_auth` 无记录 → `permissionDecision: "ask"` |
| `authorizations.json` / `task-contract.json` | 🔁 保留，是有效的预授权机制 |
| ↳ git 规则 | ✂️ 按 5.4 移除（与包一致），或明确标注为有意强化 |
| `ledger.js` + 台账 | 🔁 保留，但**只记派发**——平台的 `hook/invoked`/`hook/result` 已覆盖"钩子是否运行" |
| `orchestration/*.md` | 🔁 保留为软约束文档，**不要包装成强制** |
| 保留的真规则 | ✅ 真正值得留的是：**资源枚举类**（`DOCKER_PRUNE`、`DOCKER_REMOVE_UNSCOPED`、`DB_DESTRUCTIVE_UNSCOPED`、`RM_RECURSIVE_FORCE`）+ **发布/部署类**（`DEPLOY_NO_AUTH`、`*_PUBLISH_NO_AUTH`）+ **密钥目录类**（`SECRET_HOME_DIR`、`SECRET_DSH_CREDENTIALS`、`SECRET_SSH_KEY`）。它们的共同点是**判断"动作的破坏性/外部副作用"，而不是判断文件名** |

> ⚠️ **重开之前应先做一次独立审计。** 5.3/5.4 的结论来自一次完整精读 + 实跑验证，
> 但审计者与被审者是同一批工作流成员，**不构成包意义上的"独立门"**。
> 正式启用前，建议让一个独立成员（`code-review` 角色 + `docker-artifact-safety` / `verification-before-completion` 技能）
> 逐条复核触发条件与误判风险。这正是本工作流自己的独立门该有的用法。

## 六、明确"没必要引入"的清单

| # | 不引入 | 理由 |
|---|---|---|
| 1 | **自建路径沙箱** | `dsh-sandbox-policy` 已在每个受限调用上强制工作区边界，比正则列表**更通用**。自建是重复劳动且更弱 |
| 2 | **拦 `git commit/push`** | **包自己在 2026-09-16 移除了**（改为流程门控）；现有实现却把它加了回来（§5.4）。git 是可恢复操作（reflog / 远端），风险等级远低于删库 |
| 3 | **按"名字"判定权限** | 把 `Dockerfile`、`docker-compose.yml`、任何 `deploy/`/`k8s/` 路径段、`notes/raw/` 当危险信号（§5.3）。**目录名不是权限信号**，这会把正常工作一起锁死 |
| 4 | **为不存在的目录写规则** | `.gitlab-ci.yml` / `deploy/k8s/*` / `deploy/monitoring` / vault 在本部署都不存在 → 虚假安全感 |
| 5 | **自建工件注册表** | git 已是 revision 的事实来源；自建 JSON 必然漂移 |
| 6 | **用钩子强制流程门** | 独立 QA、工件顺序无法从工具调用判断；硬做 = 包禁止的"以提示词冒充强制" |
| 7 | **每次派发都弹审批** | 会让工作流不可用。只对**授权类别**弹（部署/推送/受保护路径/破坏性操作） |
| 8 | **用正则拦 `rm -rf`** | 表达式永远不全；真正的门是"授权 + 回滚工件"。现有实现的 `RM_RECURSIVE_FORCE` 之所以可用，是因为它**判 realpath 是否在工作区内**，不是在猜字符串 |
| 9 | **自建钩子调用审计日志** | `hook-protocol` **原生**写 `hook/invoked` + `hook/result` 会话事件。自建 JSONL 在这一层是重复的 |

第 9 条需要说清楚：平台记录的是**钩子有没有跑**，不记录**派发了几次哪个角色**。
所以角色维度的台账**仍需自建**（很小），但不能把平台的审计轨迹也算成要自建的。

**筛选原则**（把 8/9 两条合起来看）：**值得留的规则判断的是"动作的破坏性与外部副作用"，不值得留的判断的是"文件名和目录名"。**

## 七、建议的 DSH 适配设计

### 7.1 三级管道：路线决定"启用哪些门"

| | Fast | Standard（默认） | Deep |
|---|---|---|---|
| 触发 | 范围窄、解法明确、无独立门要求、回归风险低 | 常规多步骤工作 | 未决产品或持久架构决策、跨 owner 契约、敏感数据/权限、迁移、不可逆操作、强制完整独立门 |
| 派发记账 | 不派发 | ✅ | ✅ |
| 敏感动作审批（`ask`） | ✅ 始终 | ✅ 始终 | ✅ 始终 |
| 受保护路径拒绝（`deny`） | ✅ 始终 | ✅ 始终 | ✅ 始终 |
| 独立 QA | ❌（不冒充） | ✅ 软 | ✅ 软 |
| 代码审查 / 合规门 | ❌ | 必要时 | ✅ 软 |
| 工件带 revision | ❌ | 不凑模板 | ✅ |
| 任务合同完整性提醒 | — | ✅ 软 | ✅ 软 |

**注意**：前三行（记账、审批、拒绝）**与路线无关，永远开**。
它们是工具层规则，不是流程门；把它们和路线绑定只会制造漏洞（"我是 Fast 所以不用审批"）。
**路线只影响流程层的软约束。**

### 7.2 门控矩阵：每条门用什么机制、硬度多少

| 门 | 机制 | 硬度 | 状态 |
|---|---|---|---|
| 工作区边界（工作区外不可写） | `dsh-sandbox-policy` | 🔴 硬（原生） | 已装载 |
| 未授权部署/发布（`kubectl`/`terraform`/`helm`/`docker push`/`npm publish`/`gh release`） | `PreToolUse` → **`ask`** → `user-approval` | 🔴 硬 | 现有实现**改一处**即可 |
| 资源枚举不清的破坏性操作（prune、通配符删除、未命名 drop/TRUNCATE、越界 `rm -rf`） | `PreToolUse` → **`deny`**（**不提供授权出口**） | 🔴 硬 | 现有实现已具备 ✅ |
| 密钥/凭据目录（`~/.ssh`、`~/.aws`、`~/.kube`、`~/.dsh/.credentials.*`、`*.pem`） | `PreToolUse` → `deny` | 🔴 硬 | 现有实现已具备 ✅ |
| 任务契约 `denied_paths` | `PreToolUse` → `deny` | 🔴 硬 | 现有实现已具备 ✅ |
| 派发记账 | `PreToolUse(subagent)` → JSONL | ⚪ 记录 | 现有实现已具备 ✅ |
| 任务合同完整性 | `PreToolUse(subagent)` → `additionalContext` 提醒 | 🟡 软 | 待做 |
| 独立 QA / 代码审查 / 合规 | `AGENTS.md` + skill | 🟡 软（声明） | 已实现 |
| 工件链与 revision 失效 | 文件 front-matter + 比对 | 🟡 软（可核查） | 待做 |
| ~~改 `Dockerfile` / `docker-compose.yml`~~ | ~~`PreToolUse` → `deny`~~ | — | ✂️ **删**（§5.3） |
| ~~写任何 `deploy/` 或 `k8s/` 路径~~ | ~~`PreToolUse` → `deny`~~ | — | ✂️ **删**（§5.3） |
| ~~`git commit` / `git push`~~ | ~~`PreToolUse` → `ask`~~ | — | ✂️ **删**（§5.4，与包一致） |

**`deny` 与 `ask` 的分界原则**（从现有实现已有的分档里提炼）：

| | 用 `deny`（不给出口） | 用 `ask`（给人出口） |
|---|---|---|
| 判据 | 动作**不可恢复**，或**无法枚举影响范围** | 动作**明确、可枚举、有回滚工件** |
| 例子 | `docker prune`、通配符 `rm`、未命名 `dropdb`、写 `~/.ssh` | `kubectl apply` 到具名环境、`npm publish` 具名包、`docker rm mycontainer` |
| 理由 | 授权也不该放行——因为没有回滚手段 | 用户看到具体目标后可决定；批准即授权，且被平台记入会话审计日志 |

> 现有实现已经**正确地把这两档分开了**（`outright` vs `needs_auth`），
> 只是 `needs_auth` 那一档最后仍然落到 `exit 2`，没用上原生的 `ask` 通道。

### 7.3 落地形态（用 DSH 原生，不写新轮子）

```yaml
# ~/.dsh/profiles/desktop/cordis.patch.yml 里取消注释即可
- insert:
    - id: hooks-claude-code
      name: '@deepseek-ai/dsh-hooks-claude-code'
      config:
        configPath: /Users/maxwell/.dsh/team/hooks.json
        defaultTimeoutMs: 10000
```

`hooks.json` 里 matcher 只要两个：

| matcher | 判定 |
|---|---|
| `bash` | 部署/推送/破坏性命令 → `ask`（**不是 deny**，要给人授权机会） |
| `write\|edit\|str_replace_editor` | 机密文件 → `deny`；项目受保护路径 → `ask` |
| `subagent\|subagent_fork\|workflow` | **记录**合同要点到 JSONL（不阻断） |

**为什么敏感命令用 `ask` 而不是 `deny`**：包要的是"需明确用户授权"。`deny` 只能拒绝，`ask` 才是"请求授权"。硬拒绝会逼模型绕过（换个写法），`ask` 把决定交还给用户。

**fail-closed 必须自己保证**：钩子崩溃 = 非阻断（工具照常执行）。所以策略程序要在**自己内部**的异常路径上主动 `exit 2`，不能靠平台兜底。

## 八、必须诚实标注"未复刻"的部分

包 `04-验收清单.md` 要求"平台欠缺 … 记未复刻"。以下是**做不到**的：

| 能力 | 为什么做不到 |
|---|---|
| **强制 QA 独立性** | 无法判断一份报告的作者与实现者是否同一实体 |
| **强制工件顺序** | 无法判断 Tech Spec 是否在实现**之前**产生 |
| **强制"变更后旧门失效"** | 只能比对 revision 做**检查**，无法阻止引用旧报告 |
| **从工具层识别子 Agent 的角色** | `PreToolUse` 载荷无角色字段；`SubagentStart` 只有常量 `agent_type` |
| **改写工具输入** | `updatedInput` 被记录但**不生效** |
| **读取对话内容做语义判定** | `transcript_path` 恒为 `""` |
| **真正的 OS/容器级隔离** | `sandbox-policy` 是文件效应策略，不是容器隔离 |
| **按角色细分权限** | 角色是 prompt 约定，不是平台主体；平台只能按会话区分 |

**这些必须写进验收报告记「未复刻」，不能用提示词假装它们被强制了。**

## 十、总结

**DSH 能给的是"工具层硬门 + 流程层软约束"的组合。**
把流程层的东西硬做成钩子，会得到包明确禁止的"提示词冒充强制"；
把工具层的东西留在提示词里，会得到虚假安全感。

**三条最重要的结论：**

1. **这套门控已经建好了**（`~/.dsh/team/`，54K 策略程序 + 授权模型 + 台账），2026-10-14 被整体关闭。
   关掉的原因不是"不该有门控"，而是**规则面铺得太宽**：`Dockerfile`、`docker-compose.yml`、
   任何 `deploy/`、`k8s/` 路径段都被硬阻断且授权解不开。
   **一条让日常工作无法进行、却永远"正确"的规则，会连带把真正有用的规则一起拖死。**

2. **值得留的规则判断"动作的破坏性与外部副作用"；不值得留的判断"文件名和目录名"。**
   前者（prune、通配符删除、未命名删库、越界 `rm -rf`、发布部署、密钥目录）继续保留；
   后者全部删掉。分档原则：不可恢复/无法枚举影响范围 → `deny`；明确可枚举有回滚 → `ask`。

3. **包自己在 2026-09-16 就得出了同一个结论**：git 提交与推送不该在工具层硬拦，应交流程门控。
   现有实现却把它加了回来（§5.4）。**这是与来源的背离，需要明确选择，不能默认保留。**

### 11.4 顺带修掉的两个**过度阻断**缺陷

实现过程中，策略程序**拦住了它自己那份设计文档的写入**。

**缺陷 A：SQL 关键词匹配到处生效。**
`analyzeRawSql(command)` 对整条命令**原文**运行，与是否真的调用数据库客户端无关。
于是 `cat >> doc.md <<EOF ... TRUNCATE ...`、`grep "DROP DATABASE" docs/` 全被拦。
**修法**：新增 `invokesDatabaseClient()`，只在某个命令段真的执行数据库客户端
（`psql`/`mysql`/`sqlite3`/`mongosh`/`mongosh`…）时才解析 SQL 文本。

**缺陷 B：包装器的选项值被当成命令。**
`resolveCommand` 剥掉 `sudo` 之后只跳 `-` 开头的参数，于是
`sudo -u postgres psql -c "TRUNCATE orders"` 解析出的命令是 `postgres`；
同理 `sudo -u root kubectl apply` 也解析成 `root`，**部署规则被逃逸**。
**修法**：新增 `WRAPPER_VALUE_FLAGS` 表，让 `sudo -u X`、`env -u X`、`nice -n X`
这类"选项带值"的形式正确跳过。

这两个都是同一类毛病：**判定依据与真正的动作脱节**（一个是"提到词"vs"执行"，
一个是"包装器参数"vs"实际命令"）。缺陷 B 是**漏检**，比误报更值得警惕。
