# 自有配置界面可行性（2026-10-14）

> 问题：现在点卡片上的「打开插件管理」会跳到 **DeepSeekHarness 官方插件管理页**；
> 用户要的是**能配置自己这个插件的弹窗 / 界面 / 侧拉**。
> 本文是调研结论（**未改任何代码**）。所有论断都标了源码/文档出处，被我实测否证的写在 §5。

## 1. 根因：那个按钮本来就被设计成打开官方页

现行宪法 **C20.3** 定的行为是"按钮经官方公开契约 `pluginNavigation.openBundle` 打开本包"。
官方把它实现成**侧栏面板**，不是弹窗：

```js
// dsh-client-ui-plugin-manager/lib/client.js:3758-3765
const disposeNavigation = ctx.reflect.provide("pluginNavigation", { openBundle: (packageName) => {
    ctx.layout.selectPanel(PANEL_ID);                    // PANEL_ID = "plugins"（侧栏全局面板）
    instance.actions.setView({ kind: "package", name: packageName });
} });
```

`plugins` 面板的注册方式（同文件 3709-3777）：`main` keyed slot（`key: "plugins"`）+ `sidebar.panellist`（`id: "plugins"`）。
**平台没有"插件管理弹窗" API**——这是我按 `Modal` / `shell.overlay` / `main` / `sidebar.panellist` 全表查证后的结论。

所以要"配置自己的插件"，界面必须由**我们自己的客户端半侧**提供。

## 2. 平台给插件留了哪些位置（3 种，均有源码实证）

| 形态 | 机制（谁声明 / 怎么注册） | 官方同构用法 |
|---|---|---|
| **侧拉面板** | `sidebar.panellist`（list / root）：注册**图标组件** + 选项 `{id, order?, label, locale}`；**同 id** 再注册 `main`（**keyed**，`key: <id>`）作为面板页面；用 `ctx.layout.selectPanel(id)` 打开 | 官方插件管理器就是这么做的：`id/key = "plugins"`（client.js:3709-3777）。`sidebar.panellist` 由 `dsh-client-ui-sidebar` 声明（其 README.zh.md §全局面板入口） |
| **模态弹窗** | `dsh-client-ui-primitives` 导出 `Modal`：`Modal({ open, onClose, title, closeLabel, description, children, footer, className, contentClassName, onKeyDownCapture, headless, backdropBlur, shortcutModal })`，内部 `createPortal` + `useModalLayer`（顶层 Esc / Tab 走位 / 关闭后焦点归还），遮罩点击即 `onClose`（`lib/index.js:5210`） | 同包 `RiskConfirmation`（`lib/index.js:5273`）是官方风险确认弹窗；`Toast` / `HoverCard` 也在同一包 |
| **复用现有卡片浮层** | 我们现在的卡片就是个锚定 popover（`useAnchoredPosition` + portal） | —— |

补充：
- `shell.overlay` 是 `dsh-client-ui-layout` 声明并渲染的 root 槽（`lib/client.js:312` 渲染、`:617` 声明），官方插件管理器拿它挂刷新 toast（pm client.js:3702-3710）。要挂"全局常驻浮层"可以用它，但 `Modal` 自带 portal，不需要槽位。
- **官方表单外观可以直接复用**：primitives 还导出 `SettingsForm`、`SettingsFormModel`、`SettingsSecretField`、`SettingsValueField`、`settingsTextField`、`settingsNumberField`。
  `SettingsForm(props)` 读 `{ state, labels, onDiscard, children }`，`state = { available, writable, dirty, invalid, saving, failed }`；
  `SettingsFormModel(scope, specs, secrets)` 负责暂存/提交（`.shell()` / `.bind()` / `.plan()` / `.save()` 一族，class 定义在 `lib/index.js:7151`）。
  → 自建界面里的表单**能长得和官方设置页一致**，不必自己造表单框架（也不必再造一份视觉）。

## 3. 配置数据放哪：两类，别混

### A. 展示层偏好（卡片折叠、默认过滤、显隐哪些列、任务板开合）
客户端本地状态即可（localStorage / 客户端 store）。**零宿主改动、零依赖风险**，是"今天就能交付"的一类。

### B. 行为层配置（启用/停用哪些角色、每个角色的模型/通路、maxMembers、autoloadSkills 开关）
必须到宿主——派发行为由宿主半的 `/team <id>` 命令与名册决定。唯一**受支持**的客户端→宿主配置通道是**官方设置服务**：

- 宿主半声明 volatile 字段（`dsh-client-ui-settings/lib/index.js:5,10`）：
  ```js
  import z from "@deepseek-ai/schemastery";
  const Fields = { enabled: z.boolean().default(true) };
  export const Config = z.object({ enabled: Fields.enabled.volatile() });
  ```
  `.volatile()` 的字段即"可实时编辑"；写入通过**当前 profile 的 Cordis patch** 持久化，
  带 revision（防并发覆盖）、按完整 Config 校验（含不可序列化的检查）；
  Home patch / 命令行 overlay 优先级更高，**会被它们覆盖的写入会被拒绝**（`dsh-settings/README.zh.md`）。
- 客户端半（`dsh-client-ui-settings/README.zh.md`）：`ctx.configForms.get(entryId)` 拿到该 Host 条目
  **所有编辑器共享**的表单（快照含 `value/base/user/revision/writable` 与写入队列；`set`/`unset`/`mutate`）。
  条目 id 就是 profile 里那一行的 id——本机实证 `~/.dsh/profiles/desktop/cordis.yml:1276` = `- id: team-workflow`。
  还有 `ctx.configForms.describe()`（跨条目镜像）与 `whileServed(namespaces, register)`（跟随别人的命名空间）。
- "自带页面的插件"专用口子：在 `ctx.inject(['settings'], child => child.effect(() => child.settings.configure({ auto: false }, ctx.fiber)))`
  里注册 `auto: false`，**官方页就不再生成自动表单**（`dsh-client-ui-settings/lib/index.js:16`）。
- 客户端要在 `package.json` 的 `dsh.client.inject` 里加依赖：`@deepseek-ai/dsh-client-ui-settings`
  （实证：官方 `dsh-client-ui-settings-plugins/package.json` = `["@deepseek-ai/dsh-client-locale","@deepseek-ai/dsh-client-ui-settings"]`）；
  要注册面板/切面板再加 `@deepseek-ai/dsh-client-ui-layout`（`ctx.layout`）。
- **本机 profile 已挂载齐全**（实证 `cordis.yml`）：`dsh-config-editor`:58、`dsh-settings`:61、`dsh-client-ui-settings`:556、
  `dsh-client-modules`:511、`dsh-client-ui-layout`:533、`dsh-client-ui-sidebar`:541。→ 通道具备，缺的只是我们这侧接线。

## 4. 三条实现路线

### 路线 1（推荐，改动最小）自建模态弹窗
把卡片按钮从"打开官方插件管理页"改为"打开自建 `Modal`"；弹窗内用 `SettingsForm` 外观承载配置。
- 只碰客户端生成器 + 一个新组件 + i18n；不需要新槽位、不抢 main 区、不离开会话界面。
- 展示层偏好（A）立刻可用；行为层（B）在 §5 的前置解决后接上。

### 路线 2（要"侧拉"就选它）自有侧栏面板
注册自有 `sidebar.panellist` 行（自带图标 + 标签）＋ 同 id 的 `main` 页面组件，按钮改为 `ctx.layout.selectPanel("<id>")`。
- 好处：常驻、空间大、与官方同构、可声明我们自己的子槽位。
- 代价：新增入口与图标、两个槽位注册、占用 main 区（离开会话界面，要处理返回），i18n 两份。

### 路线 3（零新界面，不推荐）
配置只声明成 volatile 字段，界面仍用官方插件管理页的详情区块（我们已有 `plugins.detail.section` 挂载点）。
零 UI 成本，但正是用户不想要的，列出仅为完整性。

## 5. 硬约束与未验证项（不要读成"已可行"）

1. **`@deepseek-ai/schemastery` 从本插件路径解析不到**（实测）：
   ```
   cd /Users/maxwell/Documents/deepseek-harness/default-workspace/dsh-team-plugin
   node --input-type=module -e "import('@deepseek-ai/schemastery')" → ERR_MODULE_NOT_FOUND
   ```
   原因：`~/.dsh/profiles/desktop/node_modules/` 下只有 `@local/dsh-team-workflow`（符号链接指回工作区），
   没有 `@deepseek-ai/`；Node 按 realpath 向上找，找不到官方包。
   → 行为层配置（B）的**前置条件**，三条出路都需用户决定：
   - (i) 把插件按正常依赖 pnpm 装进 profile（走官方安装通路，官方包随依赖解析）——代价：失去"工作区符号链接即改即生效"；
   - (ii) 在 profile 的 `node_modules/@deepseek-ai/` 下补垫片/链接（`.asar` 内路径在 Electron 进程内可读）——非官方接线，**不推荐**；
   - (iii) 自建配置文件 + 自造宿主→客户端通道——成本最高（见下条）。
2. **第三方宿主插件→客户端的通用通道并不存在**（修正我先前的直觉）：`dsh-session-projection` 确实是开放 seam
   （第三方可 `ctx.inject(['sessionProjections'], …)` 注册单元，带 `wire` 块即可被客户端 `snapshot()/onChanged()` 读到），
   但它是**由已提交会话事件驱动的、逐会话的日志派生读模型**，不是通用配置通道。把"配置文件内容"塞进投影语义不合、做法可疑。
3. **未验证：HMR 能不能省掉重启**。profile 里 `hmr`（cordis.yml:9，`config.root: []`）与 `client-hmr`（:508）都在，
   `dsh-client-modules` 的 bundle revision 由 `mtimeMs/ctimeMs/size` 派生、内容变更走 `rebuilt()` 钩子进入图
   （`dsh-client-modules/README.zh.md`）。但 `hmr.root` 为空，且我们的 `client.js` 由自己的工作区脚本生成、
   不由 `dev:web` 构建 → **是否被监听未实测**。保守假设仍是改客户端要重启（C15）。
4. **未验证：`ctx.configForms.get("team-workflow")` 在真实浏览器里对本包返回可用表单**——
   逻辑上成立（条目活跃且唯一、只展示 volatile 字段），但没有在真实页面里调过一次。
5. **未验证：`Modal` 在我们生成的 bundle 壳里能否直接用**——primitives 已在我们 `dsh.client.inject` 里，
   但生成器是"官方 bundle 打补丁"，新组件的引入方式（自建 `jsx` 调用 vs. 依赖壳里的导入）需要一次实证。

## 6. 治理影响（不能跳）

- 现行 **C20.3 明文要求**按钮走 `openBundle` + 服务缺席降级 `selectPanel("plugins")`。改成自有界面 = **改宪法**，
  须走 C17：先出改动提案 → 用户确认 → 改宪法与门 6h → 改生成器 → 跑门 + 反证。
- 现有反证记录里 **M5「按钮不调 openBundle → 6f 红」会失效**，必须替换为新的反证（如"按钮不打开自有界面 → 6f 红"）。
- 当前 **25/25 的验收结论绑定现 revision**；一改代码立即失效，要重跑（C14/C19）。
- 引入 `@deepseek-ai/schemastery` 属**引入外部依赖** → 需用户明确授权（AGENTS.md §5）。
- **独立 QA 未做**（本会话策略：未获要求不派成员）→ 任何后续改动我只能自验并如实标注。

## 7. 结论与待决

技术上都做得到，且官方留了正经口子（自有面板 / `Modal` / `SettingsForm` + 官方设置传输）。
真正卡人的是一条**环境事实**（§5.1 依赖解析）与**产品事实**（配置项清单）。

待用户决定：
1. 界面形态：模态弹窗（推荐）／侧拉面板／复用卡片浮层；
2. 配置范围：只做展示层本地偏好（今天可交付）／行为层配置（先解决 §5.1）／两者都要；
3. 是否授权引入 `@deepseek-ai/schemastery`；若否，行为层配置只能走 (i) 正经安装或 (iii) 自建通道；
4. 配置项清单（要配置什么）——产品事实，需用户给；
5. 官方入口是否降级保留为次级链接（`openBundle` 仍可用）。
