# 分诊（Intake）— Fast / Standard / Deep

来源：`sources/omp/skills/team-workflow/SKILL.md`（三级复杂度门）与 `sources/omp/AGENTS.md`。
本文件是主 Agent 每次接单时的执行细则。**没有 L1/L2/L3 打分制**——那属于未生效升级草案，不得引用。

## 判定顺序

1. 先看是否命中 **Deep** 的任一触发器 → 命中即 Deep（Deep 优先于 Fast）。
2. 否则检查 **Fast** 的全部进入条件是否**同时**成立 → 全部成立才 Fast。
3. 否则 **Standard**（默认）。

不得使用的分诊依据：文件数量、token 估算、Agent 数量、任务耗时直觉。

## Fast 进入条件（须全部满足）

- 范围窄且明确；
- 解法已知、无实质设计决策；
- 无独立门（QA/审查/合规）要求；
- 回归风险低；
- 无授权/敏感数据/不可逆副作用。

Fast 执行：主 Agent 单独完成并检查受影响路径，报告实际证据。
**禁止**把主 Agent 自检写成"独立 QA"。

## Deep 触发器（任一命中）

- 未决的产品决策或持久架构决策；
- 跨 owner 契约的新增或变更（接口、schema、事件、协议）；
- 敏感数据、授权或安全边界的变更；
- 数据/结构迁移；
- 运维或不可逆副作用（部署、删除、数据修复）；
- 用户或仓库策略强制要求完整独立门。

Deep 执行：确认输入与授权 → 按依赖顺序形成必要工件（PRD→ADR（有决策才写）→Tech Spec→Implementation Plan→Test Spec）→ 只派发所需角色 → 实施 → 绑定确切 revision 的 QA + 代码审查 + 合规/安全门。
未决点以 `needs-decision` 上报；授权缺失以 `needs-authorization` 上报。**Agent 不得代批。**

## Standard 执行

1. 主 Agent 用 3–6 行说明计划与验收点（每条计划都要有对应验证）。
2. 派发时写任务合同；多个实施者可并行，但**允许路径必须互不重叠**。
3. 共享文件必须指定唯一集成者。
4. 独立 `qa` 核对结果 revision；缺陷回 owner 修复并重跑受影响门。
5. 不为凑模板生产 PRD/ADR/Tech Spec。

## 升级与降级

- 调查中风险扩大 → **继续之前**重新分诊，并说明升级理由。
- 不得倒填：未执行的门不得在报告里写成已执行。
- 显式用户要求与仓库/生效策略要求**覆盖**路线捷径（例如用户要求 Fast 也必须独立 QA，则必须做）。

## 纯文档/调研任务

QA 核查请求的**可观察交付物**（文件存在性、内容准确性、链接、格式、来源引用），
**不编造测试运行**，不声称运行了不存在的测试。

## 输出格式（主 Agent 每次接单必须给出）

```text
路线：Fast | Standard | Deep
理由：<命中/排除的具体条件>
需要的决策：<无 | 具体未决点，归谁>
需要的授权：<无 | 具体动作与目标>
计划与验收点：<3–6 行>
```
