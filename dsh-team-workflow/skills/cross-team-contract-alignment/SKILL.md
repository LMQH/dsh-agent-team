## When to Use

跨团队对接/联调前、发现接口定义分叉、联调缺口频发、或任一方变更接口语义时必读。

# 跨团队联调接口契约防漂移

## 触发条件

- 跨团队联调/对接（本项目 = 智枢 SynCore ↔ 业务平台 Mozin）
- 两个系统各有自己的 API 方案，联调前发现接口定义分叉
- 联调冒出大量"缺口"、字段对不上、错误码对不上、鉴权方式对不上
- 任意一方改了接口语义（架构升级、状态机升级）后未同步

## 核心认知：三类缺口，归因不要一刀切

出现联调缺口时**先三分类**，不同类别的处理完全不同，避免误判责任或盲目返工：

| 类别 | 定义 | 处理 |
|------|------|------|
| **契约漂移** | 双方各持不同的 wire 定义（路径/字段/错误码/鉴权） | 回契约层对齐，定责后改，改走版本号 |
| **实现偏差** | 一方没按已AB的契约实现 | 改代码，不改契约 |
| **环境/配置** | 地址、密钥、代理、部署未就绪 | 成本最低，最先解决 |

⚠️ 大量"联调缺口"本质是**契约漂移**，不是功能缺陷——正因为联调前没有单一权威契约，双方才各自凭空定了一套 wire 定义。

## 契约升级后第一步永远是重产字段级契约（不是先写实现）

接口/编排语义一升级，正确顺序是：

```
架构决策（ADR）→ 字段级接口契约（wire 定义）→ 分工实现
    ↑ 状态机/对象模型定了，          ↑ 必须有，否则下游没法干活
      第一件事重写 API 规约
```

区分两类契约，缺一不可：
- **架构契约**（责任边界）：谁写谁读、状态机归属、Gate/幂等语义、数据所有权 —— 决策性文档
- **字段级 wire 契约**：每个端点的方法/路径/请求体字段/响应体字段/错误码全集/鉴权/幂等 —— 可被客户端直接生成代码

**必须有一个"单一权威源"**：不管在供应商 repo 还是消费方 repo，全项目只能有一份，另一方是引用/镜像；**绝不允许两边各持一份还能各自改**。谁定契约，谁负责把 openapi.yaml / schema.json 定稿并**主动推给对方**，不是等对方来拉。

## 联调前强制安检：契约静态比对（门控步骤）

在任何联调动作之前，加一个不可跳过的门控：

```
1. 拉取对方契约文件（openapi.yaml / schema.json）到本地 repo
2. 逐端点逐字段机器比对：路径 / 方法 / 请求字段 / 响应字段 / 错误码 / 鉴权
3. 产出「比对报告 + 差异清单」，按差异定责（哪个缺口算哪方返工）
4. 差异全部关闭或明确标注"联调时确认项"后，才允许开始联调
```

- 比对用工具（`openapi-diff` / json-schema diff / 脚本按字段扫），不要人肉对
- 这个步骤要排进任务清单的**联调前批次第一项**，不要被实现缺口掩盖
- 本技能与 `api-contract-testing` 互补：本技能管"联调前契约对齐"，`api-contract-testing` 管"接口测试/Postman 验证"，是它的上游

## 契约变更纪律（版本 + 通知，不静默改）

- 契约变更**必走版本号 + 归档留痕**，同版本禁止反复增补（与项目 memory「契约冻结语义」一致）
- 变更要**同步通知对方并确认收到**，不是自己改了就算
- 双方各维护一份**变更日志**，联调发现不一致先查日志定位是哪个版本引入

## 关键证据链（本次智枢↔Mozin 实证，可复用为复盘模板）

- 智枢 v1.2「01 接口与对接」目录只有：P1 契约 V1.0.2（内部编排对象，非 wire 字段）、边界划定 V1.1.0（责任归属）、工具 Mock 交接；**无 v1.2 字段级权威契约**
- 真正的字段级文档「智枢接口文档 V1.0.8（13端点+error.code 全集）」被归档为 v1.1 只读禁止引用，v1.2 未重产
- Mozin 侧「联调清单.md」引用的 `contracts/openapi.yaml`(2541行)+ `syncore/*.schema.json` 在**Mozin 自己的 GitLab repo**，智枢 repo 里没有 contracts/ 目录（G7 缺口明文"从 Mozin GitLab 拉 contracts/ 比对" = 联调前从未拉过）
- 结果：智枢持 `route.selected`/`GATE_REQUIRED`/工作负载凭证那套，Mozin 持 `template_id`/`SYNCORE_GATE_REJECTED`/JWT HS256 那套，两套 wire 定义互不认识 → G1~G10 十个"缺口"
- 责任结论：主责在契约定稿方（供应商）——语义升级了但**字段级契约从未产出/推送**，消费方只能凭空自定 → 这不是"对方没搞懂"，是"上游没给可对齐的锚点"

## 落地可验动作（下次联调前逐项打勾）

- [ ] 产出/更新字段级契约（openapi.yaml 或 schema.json），单一权威源
- [ ] 主动推送契约给对方 repo / 群（不是等对方拉）
- [ ] 联调前批次的第一个任务 = 契约静态比对 + 差异定责
- [ ] 契约变更走版本号 + 归档，同版本不增补
- [ ] 变更通知对方并确认收到
- [ ] 联调缺口先三分类（漂移/偏差/环境），再决定改契约还是改代码
