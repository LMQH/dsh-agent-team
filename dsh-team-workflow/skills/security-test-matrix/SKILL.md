# Security Test Matrix — 安全测试矩阵

**核心原则：安全测试不是"全测一遍"，而是按"钱>权限>数据"分优先级，对高风险功能用三类测试矩阵覆盖。用最小的成本发现最大的风险。**

## 与其他安全 skill 的分工

| skill | 视角 | 方法 | 适用场景 |
|-------|------|------|---------|
| `gstack-cso` | 技术层 | OWASP Top 10 + STRIDE + supply chain | 全面技术安全审计 |
| `gsd-secure-phase` | 流程层 | 回顾性威胁缓解验证 | GSD phase 完成后 |
| **本 skill** | **业务层** | **P0-P3 优先级 + 正常/边界/异常三类矩阵** | **功能交付前/上线前** |
| `anti-fake-testing` | 测试质量层 | 故意改错验证测试有效性 | 验证测试不是假的 |

**一句话区分**：CSO 查"代码有没有技术漏洞"，本 skill 查"业务功能有没有安全风险"，防假测试查"安全测试本身是不是假的"。

## 8 步安全审计流程

### 第一步：分清主次 — 确定安全审计优先级

**判断标准**：按"钱 > 权限 > 数据"递降排序

| 优先级 | 特征 | 举例 |
|-------|------|------|
| **P0 — 最高** | 涉及金钱、支付、余额 | 订单、支付回调、退款 |
| **P1 — 高** | 涉及权限控制、用户身份 | 登录、注册、角色管理、API 鉴权 |
| **P2 — 中** | 涉及用户数据读写 | 个人信息、内容管理 CRUD |
| **P3 — 低** | 涉及展示类、无敏感操作 | 静态页面、公告、首页 |

**操作**：将项目所有功能按上表分级。

### 第二步：构建三类测试覆盖矩阵

针对 P0/P1/P2 功能，逐项列出三类测试用例：

| 测试类型 | 定义 | 举例（登录接口） |
|---------|------|----------------|
| **正常** | 正确的输入，预期成功 | 正确账号+密码登录成功 |
| **边界** | 刚好在限制边缘 | 密码最短/最长长度、用户名最大长度 |
| **异常** | 故意错误的输入 | 空密码、SQL 注入 payload、特殊字符、不存在的用户 |

### 第三步：安全攻防测试

#### 3.1 认证（Authentication）

检查内容：
- 未登录状态下能否调用该接口？
- Token/Session 过期后是否返回 401 而非 200？
- 登录失败有次数限制或延迟吗？

#### 3.2 授权（Authorization）

检查内容：
- 用户 A 能否操作属于用户 B 的数据？（数据越权）
- 普通用户能否调用管理员权限的接口？（功能越权）
- 权限校验在后端还是在仅前端？（必须后端）

#### 3.3 输入校验（Input Validation）

检查内容：
- 所有用户输入是否在后端做了类型/长度/格式校验？
- 数据库查询是否使用了参数化查询（防注入）？
- 返回结果中是否泄露了敏感信息（密码、Token、密钥等）？

#### 3.4 数据归属（Data Ownership）

检查内容：
- 查询数据时是否校验了 owner_id / user_id 必须等于当前登录用户？
- 如果用户修改了 URL 中的 ID 参数，能否看到他人的数据？
- 批量查询接口是否限制了只能查询属于自己的数据？

### 第四步：防假测试

**此步骤调用 `anti-fake-testing` skill 执行。**

对 P0/P1 功能的权限校验逻辑做"故意改错→跑测试→看能否抓到"验证。

### 第五步：自动回归网

将安全测试用例改写成可执行的测试代码，集成到项目的测试框架中：
- 每个测试用例独立可运行
- 测试失败时有清晰的错误信息
- 不依赖外部环境（使用 Mock 或测试数据库）

### 第六步：部署安全审查

| 部署方式 | 安全重点 |
|---------|---------|
| 原生部署 | 运行用户（不用 root）、文件权限（644/755）、服务隔离 |
| Docker | 镜像来源（只用官方/可信）、容器非 root 运行、资源限制 |
| 面板部署 | 独立强密码、访问来源限制、及时更新面板版本 |

### 第七步：上线前最终自检

1. 检查代码中是否有写死的密钥、Token、密码
2. 检查是否有调试代码（console.log / print / var_dump / dd）
3. 检查是否有注释掉的校验逻辑
4. 检查 .env 是否在 .gitignore 中
5. 列出所有暴露在公网的端口和服务

### 第八步：安全审计报告

```
## 安全审计报告 — [项目名] — [日期]

### 本次审计范围
- P0 功能：[数量]个
- P1 功能：[数量]个
- P2 功能：[数量]个

### 测试执行情况
- 三类测试用例：[总数量]条（正常/边界/异常）
- 安全攻防测试：[通过/未通过]
- 防假测试：[通过/未通过]

### 发现的问题
| 编号 | 严重程度 | 问题描述 | 修复状态 |
|------|----------|----------|----------|
| 1 | P0 | ... | 已修复 |

### 部署安全审查
- 原生/Docker/面板：[通过/未通过]
- 存在风险：[列出]

### 结论
- [ ] 可以上线
- [ ] 修复后上线
- [ ] 禁止上线
```

## 频率建议

| 阶段 | 执行内容 | 频率 |
|------|---------|------|
| 日常开发 | 输入校验 + 数据归属检查 | 每次提交前 |
| 功能完成 | 三类测试 + 安全攻防 + 防假测试 | 每个功能交付前 |
| 上线前 | 完整闭环（全部 8 步）+ 审计报告 | 每次上线前 |
| 定期维护 | 依赖安全扫描 + 部署环境审查 | 每月一次 |

## 五句安全口诀

```
认证分开查：登录归登录，权限归权限
输入全不信：所有用户输入后端二次校验
数据要验主：每个查询问一句「这数据是他的吗」
改错验测试：故意改坏代码，看测试能抓住吗
部署最小化：权限最小、端口最少、用户不 root
```

## 常见陷阱

| 陷阱 | 表现 | 正确做法 |
|------|------|---------|
| 只看正常路径 | 边界和异常场景完全没测 | 三类测试缺一不可 |
| 前端校验当安全 | 以为用户不能修改前端 JS | **后端必须做独立校验** |
| 测试代码造假 | 测试跑过了但什么都没断言 | 执行防假测试 |
| 只在开发环境测 | 部署到生产环境配置不对 | 部署前先跑部署检查清单 |
| 密钥写死在代码里 | .env 不在 .gitignore | 首次提交前就设好 .gitignore |
| 权限只校验一次 | 登录时校验了，之后每个接口不校验 | 每个接口独立校验权限 |
| 日志不脱敏 | 把用户密码、Token 直接打日志 | 日志中密码/Token 必须 mask |
| 过度测试 P3 | 花大量时间测 P3，P0 反而没时间 | 严格按优先级分配测试时间 |
| 没留证据 | 上线后出问题无法追溯 | 每次闭环产出审计报告 |
