# 架构决策冲突模式（方案级审查补充）

> 沉淀自 2026-09-05 syncore-server M7「数据对齐业务平台」可行性分析会话。适用于里程碑可行性分析、方案审查、推送门控时对方案层（非代码层）的缺陷对照。

## 模式 A：任务表述与已接受 ADR 语义冲突

- **现象**：任务/排期条目的字面动作直接违反已落盘 ADR。实例 = M7「新建数据表 + 全量会话消息映射对齐」vs ADR-006「业务平台侧不投影执行记录、只存引用句柄」（syncore-server，2026-09-05 分析确认）。
- **审查方法**：里程碑可行性分析时，逐条把任务子项与 `docs/v2.0/02_系统设计/03_架构决策ADR/syncore-adr/` 下已接受 ADR 对照；不能只查「有没有提到」，要查语义方向是否相反（建副本 vs 只存句柄）。
- **处置**：冲突 ≠ 不能做，而是开工前必须二选一——①改任务表述对齐 ADR（如「建表」→「建引用句柄映射表」）；②修订/补充 ADR 说明例外。此即宪法硬门控 #2「超出 ADR 必须暂停」的触发场景。
- **结论输出格式**：可行性按「现在可做 / 等拍板 / 等依赖」三档分类；阻塞点区分「依赖链缺失」（如上游契约 M4-C2 未落盘，排期问题）与「语义冲突」（需用户决策，门控问题）两类，勿混为一谈。

## 模式 B：文档与源码双向漂移

- **现象**：接口存在性声称只引文档会被证伪——文档可能滞后（新路由未收录）或超前（写了未实现的能力）。
- **审查方法**：对接/对齐类方案，接口清单须以源码路由注册为权威核验：
  - 路由：`rg 'r\.(Get|Post)\("/api/…' core_src/server/cmd/server/router.go`
  - 鉴权：`core_src/server/internal/middleware/auth.go` 前缀分流（`mul_` PAT / `mdt_` Daemon / `mat_` task token / `mcn_` cloud / JWT）
  - 引用行号必须标注快照日期（行号随上游演进漂移）。
- **实例（2026-09-05 核实）**：Multica 对外仅轮询式接口（issues / task-runs / tasks/{id}/messages / chat/sessions/{id}/messages），WebSocket `/api/daemon/ws` 是 `mdt_` 内部通道，外部消费者用不了——「全量同步」只能轮询。只看文档容易误以为有推送通道可用。

## 模式 C：里程碑依赖链核查

- 任务清单（`docs/v2.0/03_技术方案/01_开发组织/SynCore-Multica2.0-服务端建设任务清单.md`）是飞书清单的本地镜像，**状态以飞书为准**；依赖标注（如「依赖 C2 契约」）要看上游契约/方案文档是否真的落盘，未落盘 = 硬依赖阻塞，该子项只能出调研草案不能动实现。
