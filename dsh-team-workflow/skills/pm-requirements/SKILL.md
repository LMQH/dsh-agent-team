# PM Requirements — 产品需求管理

**核心理念：需求不锁死就写代码 = 后面大面积返工。SOP-01 的 7 步流程确保在写第一行代码前，产品需求已经完整、分级、可验证。**

## 定位

本 skill 是**产品经理/需求方视角**的标准化工作流。与工程侧 skill 的分工：

| Skill | 视角 | 场景 |
|-------|------|------|
| **本 skill** | 产品经理 | 从想法到功能清单到 MVP 定义 |
| `grill-me` | 通用 | 需求拷问，开工前澄清歧义 |
| `brainstorming` | 通用 | 想法探索和验证 |
| `project-bootstrap` | 工程师 | 技术选型 + 骨架搭建（以功能清单为前提） |
| `agent-constitution-generator` | 工程师 | Agent 宪法生成（以技术栈为前提） |

**流程**：`pm-requirements`（本 skill）→ `project-bootstrap`（搭骨架）→ 编码开发

## 产品边界

产品需求只定义用户可观察的结果：目标用户、价值、能力、范围、非目标、流程、状态、优先级和可验收标准。

产品需求不得规定数据库字段或表、接口 payload 或错误码、凭据格式或存储、内部服务、运行时路由、算法、文件结构或调用顺序。若某技术约束影响用户可见能力，可将它表达为产品不变式或非功能要求，但实现方式交给 ADR 和技术方案。

产品经理不得以架构 ADR、已有实现或技术便利性反推产品范围。产品未决定的能力、商业形态、用户体验或 MVP 归属必须标为产品待决项；不得由 ADR 代为选择。

若能力、角色、是否纳入 MVP 或可观察行为尚未确定，返回 `needs-decision`。不得即使以条件形式为某个流程或验收标准标注 P0/P1/P2；优先级只能在产品负责人批准该行为后确定。

## 前置条件

| # | 条件 | 说明 |
|---|------|------|
| 1 | 有一个产品想法 | 哪怕只有一句话（"我想做一个二手书交易小程序"） |
| 2 | 准备了一个空的项目文件夹 | 后续 <project>/delivery/DevDocs 就建在这里面 |
| 3 | 准备好回答 AI 的灵魂拷问 | 目标用户是谁？解决了什么痛点？最核心的功能是什么？ |

## 需求真实性诊断（YC 六原则，蒸馏自 gstack-office-hours）

写 PRD 前先过一遍，模糊回答要追问到底：

1. **具体性是唯一货币** — "医疗行业的企业"不是客户，"张三、某角色、某公司、某个具体理由"才是。说"人人都需要"= 找不到任何人。
2. **兴趣 ≠ 需求** — 注册数、点赞、"挺有意思"都不算。行为、付费、服务挂了 20 分钟客户就来电话——这才算需求。
3. **用户原话 > 创始人话术** — 用户实际描述的价值和 pitch 不一致时，用户的版本才是真相，照它改文案。
4. **看操作，别演示** — 引导式 walkthrough 学不到真用法；坐在用户背后看他自己挣扎才学得到。没做过就先去做，这是第一作业。
5. **现状土办法才是真对手** — 不是竞品，是用户现在凑合用的"表格+群消息"方案。若现状是"什么都不用"，多半说明痛点不够痛。
6. **窄胜于宽** — 本周就有人愿真金白银买单的最小版本 > 完整平台愿景。先楔子，再扩张。

## 7 步标准流程

```
Step 1: 想法陈述 ── 把大脑里的东西倒出来
  ↓
Step 2: 立项说明书 ── 结构化项目提案
  ↓
Step 3: 功能清单 ── P0/P1/P2 优先级分级
  ↓
Step 4: 三种拆法 ── 按角色/流程/模块细化
  ↓
Step 5: 划分大阶段 ── MVP 定义 + 不做清单
  ↓
Step 6: Agent 宪法 ── AI 行为守则（如已有技术栈决策）
  ↓
Step 7: <project>/delivery/DevDocs 归档 ── 文档体系索引
```

---

### Step 1：想法陈述 — 把大脑里的东西倒出来

**做什么**：用最自然的方式把你的想法说给 AI 听，倒出所有零碎的想法，不追求结构。

**产出的原始想法记录**（200-500 字），包含：
- 你想做什么产品/功能？
- 为什么要做？（解决了什么痛点？）
- 目标用户是谁？
- 你最核心的功能是什么？
- 有没有参考产品？（竞品或灵感来源）

**AI 会追问的"灵魂拷问"**：
1. 没有这个产品，用户现在怎么解决这个问题？
2. 为什么是你来做？（你的独特优势是什么？）
3. 最坏情况下，这个产品一周能做出来吗？如果能，这一周做什么？
4. 用户凭什么愿意用？（上瘾点是什么？）

---

### Step 2：输出立项说明书

**产出**：`<project>/delivery/DevDocs/01-立项说明书.md`

**文档结构**：
```
# 立项说明书 — [项目名]

## 产品概述（一句话）
[用一句话说清这个产品是什么]

## 目标用户
- 用户画像 1：[描述] — 痛点：[…]
- 用户画像 2：[描述] — 痛点：[…]

## 核心功能（3-5 条）
1. [功能 1] — 为什么必须有它？
2. [功能 2] — 为什么必须有它？
3. [功能 3] — 为什么必须有它？

## 明确不做的事情（排除范围）
- 不做 [XX] — 因为 [理由]
- 不做 [XX] — 因为 [理由]

## 成功指标
- 上线后如何判断做对了？（可量化的指标）

## 核心用户流程（一句话）
用户从 [A] 到 [B] 的最短路径是：...
```

---

### Step 3：拆功能清单（P0/P1/P2 分级）

**产出**：`<project>/delivery/DevDocs/02-功能清单.md`

**分级规则**：

| 优先级 | 含义 | 规则 |
|-------|------|------|
| **P0** | MVP 必须有 | 删掉它=产品不可用。只选能跑通一条核心用户流程的 |
| **P1** | 第一版应该有 | 显著提升体验，但删掉产品仍能用 |
| **P2** | 后续版本再加 | 锦上添花，第一版不做 |

**每个功能包含**：
```
### [P0] 用户注册与登录
- 用户故事：作为一个新用户，我可以注册账号并登录
- 验收标准：注册成功后发送验证邮件，登录后进入首页
- 实现阶段：MVP（阶段一）
```

---

### Step 4：三种方法拆功能进一步细化

**三选一或组合使用**，把大功能拆成可在 1-3 次 AI 会话内完成的小任务。

| 方法 | 适用场景 | 举例 |
|------|---------|------|
| **按角色拆** | 有多个用户角色 | 买家、卖家、管理员各一套功能流 |
| **按流程拆** | 功能之间有清晰的先后顺序 | 注册→选商品→下单→支付→发货→收货 |
| **按模块拆** | 功能间相对独立 | 用户中心、商品管理、订单系统、消息通知 |

**操作**：对 P0 功能的每个核心流程，用最适合的方法拆出可执行的小任务列表。

---

### Step 5：划分大阶段 — 定义 MVP

**产出**：`<project>/delivery/DevDocs/03-阶段计划.md`

**核心原则**：**MVP 只跑通一个完整的核心流程**，不贪多。

**阶段计划结构**：
```
# 阶段计划 — [项目名]

## 阶段一：MVP（上线）
- 目标：[一句话——完成后产品能做什么]
- 功能：[从 P0 中选出的最小集合]
- 验收标准：[用户从 A 到 B 的最短路径，跑通则 MVP 合格]

### 本阶段不做的事情（明确排除）
- 不做 [XX]
- 不做 [XX]

## 阶段二：[名称]
- 目标：[…]
- 功能：[…]

### 本阶段不做的事情
- 不做 [XX]

## 阶段三：[名称]
...
```

**MVP 铁律**：如果你觉得"阶段一还需要 XX 功能才算完整"——那就先不加。MVP 是"最小可跑通"，不是"第一期"。每多一个功能就多两周开发时间。

---

### Step 6：Agent 宪法

**做什么**：如果技术栈尚未确定，先输出一份精简的开发规范框架。如果技术栈已定，调用 `agent-constitution-generator` 生成完整宪法。

**在需求阶段只需产出**：
```
/.ai-rules.md（精简版）
- 项目目标（从立项说明书取一句话）
- 开发阶段划分（从阶段计划取阶段定义）
- 当前阶段不做的事情（防止功能漂移）
- 文档索引（<project>/delivery/DevDocs 路径）
```

**完整宪法在技术选型后由 `agent-constitution-generator` 生成**（在 `project-bootstrap` Step 6 调用）。

> DSH 迁移说明：`agent-constitution-generator` / `project-bootstrap` 不在本迁移包内（见 `../CONVERSION-NOTES.md`）。DSH 中项目级生效规则的载体是指令层（`instructions/`，含 `AGENTS.md`）；本包不配置 `.ai-rules.md`，也不宣称该文件存在。

---

### Step 7：归档 <project>/delivery/DevDocs 文档体系

**最终产出目录**：
```
<project>/
└── delivery/
    └── DevDocs/
        ├── 01-立项说明书.md      ← 产品概述 + 目标用户 + 核心功能 + 排除范围
        ├── 02-功能清单.md        ← P0/P1/P2 分级 + 用户故事 + 验收标准
        ├── 03-阶段计划.md        ← 阶段划分 + MVP 定义 + 不做清单
        └── .ai-rules.md          ← Agent 宪法（精简版，或引用 AGENT_CONSTITUTION.md）
```

**验证**：
- [ ] 随便抽一个功能问 AI："这是哪个阶段的？验收标准是什么？"AI 能答对
- [ ] 文档写完后的需求变更已同步更新 <project>/delivery/DevDocs
- [ ] MVP 阶段的功能集合 ≤ P0 且能跑通一条完整用户流程

## 验收标准

| # | 验收项 | 通过条件 |
|---|-------|---------|
| 1 | 立项说明书 | 文档完整，含产品概述/目标用户/核心功能/排除范围 |
| 2 | 功能清单 | 按 P0/P1/P2 分级，每项有用户故事 |
| 3 | 功能拆分 | 大功能已拆成可在 1-3 次 AI 会话完成的小任务 |
| 4 | 阶段计划 | MVP 定义清晰，能跑通一条完整核心流程，所有阶段有不做清单 |
| 5 | Agent 宪法 | 技术栈约束、代码规范、安全底线（至少精简版） |
| 6 | 目录完整性 | <project>/delivery/DevDocs 下 3 个文件齐全 |
| 7 | 防漂移验证 | 随便抽一个功能问 AI 它能准确回答阶段归属和验收标准 |

## 常见陷阱

| # | 陷阱 | 后果 | 预防 |
|---|------|------|------|
| 1 | **立项阶段就让 AI 写代码** | 需求没锁死就开写，后面大面积返工 | 严格执行"先文档后代码"，立项阶段只用 AI 做文档助手 |
| 2 | **功能清单不分优先级** | AI 不知道先做什么，各方向同时开工 | 强制 P0/P1/P2 分级，MVP 只选 P0 |
| 3 | **MVP 定义太宽** | 第一版就做了一堆功能，迟迟上不了线 | MVP 只跑通一条核心用户流程，其他都是"以后再说" |
| 4 | **阶段不做明确排除** | AI 做着做着跑到隔壁功能去了 | 每个阶段必须写"本阶段不做的事情" |
| 5 | **忽略 Agent 宪法** | AI 每次开工都要重新理解上下文 | 宪法放项目根目录，开头说清楚让 AI 先读 |
| 6 | **文档写完后不更新** | 后面做决定时和原始文档冲突 | 阶段推进中如有需求变更，同步更新 <project>/delivery/DevDocs 并写明变更原因 |
| 7 | **文档不保存到项目本地** | 换台机器或换个人就找不到原始立项思路 | 所有文档放项目本地 `<project>/delivery/DevDocs/` |

## 培训要点

### 给产品经理的核心认知

1. **想法写清楚本身就是一个验证过程** —— 写完立项说明书后如果觉得"好像也没那么值得做"，那就对了，比写几周代码后再发现好
2. **功能清单写了 30 个，MVP 选 3 个够吗？** —— 如果那 3 个能跑通一个完整用户流程，那就够。MVP 是"最小可跑通"，不是"最小功能数"
3. **Agent 宪法是一次写完就不用管了吗？** —— 不是。技术栈变更、项目规模扩大后都要回头看

## 与其他 skill 的协作

```
用户输入 PRD / 产品需求
  └→ pm-requirements (本 skill：7 步产品需求流程)
       ├→ brainstorming (Step 1: 想法探索)
       ├→ grill-me (需求澄清)
       ├→ agent-constitution-generator (Step 6: 宪法，可延迟到技术选型后)
       └→ 产出 <project>/delivery/DevDocs/{01-立项,02-功能清单,03-阶段计划}
            └→ project-bootstrap (技术选型 + 骨架搭建)
                 └→ 编码开发 → 测试验证
```

| 阶段 | 负责 skill | 产出物 | 面向角色 |
|------|-----------|-------|---------|
| 需求定义 | **本 skill** | <project>/delivery/DevDocs/01-03 + 精简宪法 | 产品经理 |
| 需求澄清 | `grill-me` | 澄清后的需求边界 | 产品经理 |
| 技术选型 | `project-bootstrap` | 架构文档 + 技术栈 + 后端/前端骨架 | 工程师 |
| 宪法生成 | `agent-constitution-generator` | AGENT_CONSTITUTION.md | 所有人 |
| 开发执行 | 编码 + 测试 | PLAN.md + 代码 | 工程师 |
