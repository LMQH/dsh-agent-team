# Verification Before Completion

## 核心铁律

**在没有运行验证命令并确认输出之前，不能声称任务完成。**

"我觉得做完了"不是完成。"测试通过了"才是完成。

### 改动传导验证（2026-09-14 实战教训）

**改了投递方式/契约/格式/配置，必须到消费端实测效果。写入端通过 ≠ 消费端生效。**

改 A 供给、B 消费时，验证对象是 B 的实际行为，不是 A 的账本：

- 改了数据投递方式 → 到读取方实测能读到
- 改了 API 契约 → 到前端/调用方实测渲染和功能
- 改了消息格式 → 到消费者实测能解析
- 改了配置下发 → 到执行端实测配置真的生效

只验证写入端（DB 有记录、接口 2xx、脚本 exit 0）就宣称完成 = 假完成。

**四条常见假阳性**（每条都是真实踩过的坑）：

1. ❌ 只查 DB/账本有记录 → 表可能无消费者，记录 ≠ 生效
2. ❌ 只 curl API 看 JSON 返回 → API 返回 ≠ 前端实际渲染（前端还有白名单/feature flag 等条件）
3. ❌ 引用旧验收报告作为「通过」依据 → 代码改造后旧报告失效，必须重跑
4. ❌ 容器日志还在跳 → 可能是旧容器心跳；用 `docker inspect --format '{{.Config.Image}}'` 确认镜像真换了

## 什么时候用

- 在任何任务声称完成之前
- 在说"搞定了""done""完成了"之前
- 在 plan 的每个任务完成后、进入下一任务前
- 在 `subagent` 子代理返回结果后验证其声称（返回值 ≠ 事实，须到消费端核实）

## 验证清单

### 1. 代码验证

```bash
# 语法检查
python -m py_compile <file>        # Python
npx tsc --noEmit                   # TypeScript
cargo check                        # Rust
go build ./...                     # Go
```

### 2. 测试验证

```bash
# 运行相关测试
python -m pytest <test_file> -v
npm test -- --passWithNoTests
cargo test
go test ./...
```

### 3. 功能验证

- 如果有自动化测试 → 运行测试
- 如果没有测试 → 写一个验证脚本
- 如果无法自动化 → 手动验证并记录步骤

### 4. 变更验证

```bash
# 确认变更确实存在
git diff --stat
git diff --name-only
```

### 5. 回归验证

```bash
# 确认没有破坏其他东西
# 运行全量测试或受影响模块的测试
```

### 5. 三种走法验证（补充检查）

借鉴 VibeCoding SOP-03 手动测试闭环方法论，声称完成前应覆盖以下三条路径：

| 路径 | 描述 | 验证方式 |
|------|------|---------|
| **主流程走通** | 正常操作从头走到尾，结果符合预期 | 运行核心功能测试 |
| **歪路专门走** | 异常路径：不登录/空输入/负数/越权 ID/超长字符串 | 运行异常路径测试或手动验证 |
| **被牵连的地方没坏** | 改 A 后 B 依然能用（回归） | 运行受影响模块的测试 |

**最低要求**：
- ✅ 主流程测试通过（硬要求）
- ✅ 至少一条异常路径测试通过（硬要求）
- ✅ 受影响模块回归测试通过（硬要求）

**如果项目没有异常路径测试**：至少手动验证一条异常路径（如传空值、非法 ID），记录验证结果。

**输出补充**：

```
三种走法验证:
  ✅ 主流程: [测试命令] → PASS
  ✅ 异常路径: [测试命令 或 手动验证描述] → PASS
  ✅ 回归: [测试命令] → PASS
```

或：

```
三种走法验证:
  ✅ 主流程: PASS
  ⚠️ 异常路径: 无自动化测试，手动验证: [描述] → PASS
  ✅ 回归: PASS
```

### 6. 防假测试验证（可选但推荐）

借鉴 VibeCoding SOP-03/04 防假测试方法论，当本次变更涉及以下高风险逻辑时，建议额外执行一次防假测试：

| 触发条件 | 说明 |
|---------|------|
| 变更涉及权限校验 | 角色检查、owner_id 校验、API 鉴权 |
| 变更涉及金额计算 | 支付、退款、余额、价格计算 |
| 变更涉及输入校验 | 类型/长度/格式检查、SQL 查询条件 |
| 变更涉及数据归属 | WHERE user_id = ? 等 ownership 过滤 |

**执行方式**：调用 `anti-fake-testing` skill，对 1-3 个关键逻辑点做"故意改错→跑测试→看能否抓到"验证。

**最低要求**：不强制执行，但若跳过，需在验证报告中标注"⚠️ 防假测试: 未执行"。

**输出补充**：

```
防假测试验证:
  ✅ 已执行: [逻辑点1] → 改错后测试 FAILED (真测试)
  ✅ 已执行: [逻辑点2] → 改错后测试 FAILED (真测试)
  ⚠️ 未执行 (本次变更不涉及高风险逻辑)
```

## 流程

```
Step 1: 确定验证标准 — 什么叫做"完成"？
Step 2: 运行验证命令 — 实际执行，不靠推理
Step 3: 检查输出 — 通过/失败？
Step 4: 如果失败 → 回到实现，修复后重新验证
Step 5: 三种走法验证 — 主流程 + 异常路径 + 回归
Step 6: 防假测试验证 — 涉及高风险逻辑时可选执行（调用 anti-fake-testing）
Step 7: 如果通过 → 记录验证证据 → 才能声称完成
```

## 输出格式

```
Verification Report
===================
任务: [描述]
验证时间: [时间]

验证结果:
  ✅ 语法检查: [命令] → PASS
  ✅ 单元测试: [命令] → 12 passed, 0 failed
  ✅ 功能验证: [命令] → PASS
  ✅ 变更存在: [文件列表]
  ✅ 回归测试: [命令] → 全部通过

决议: VERIFIED ✓
```

或：

```
Verification Report
===================
任务: [描述]
验证时间: [时间]

验证结果:
  ✅ 语法检查: PASS
  ❌ 单元测试: 2 failed
     - test_user_creation: AssertionError
     - test_user_validation: TypeError

决议: NOT VERIFIED ✗ — 需要修复后重新验证
```

## 常见反模式

| 反模式 | 正确做法 |
|--------|---------|
| "我写完了" | 运行验证命令 |
| "应该没问题" | 实际运行测试 |
| "测试在我脑子里过了" | 在终端里过 |
| 跳过回归测试 | 至少跑受影响模块 |
| 子代理说"已完成" | 验证其产出（文件存在、测试通过） |

## 与其他 skill 的关系

```
执行实现
  → verification-before-completion (每个 plan 完成后)
  → requesting-code-review (审查)
  → 交付/发布
```

在任务收尾流程中的位置：
- 所有任务完成前最后一步
- 极速管道（Fast）：至少做语法检查
- 标准管道（Standard）：做测试 + 变更验证
- 深度管道（Deep）：全量验证清单
